AI Product Method

Prompt Engineering 科学化探索

Prompt Engineering 不是把一句话改得更顺，而是在固定模型之上做 AI 行为优化： 定义产品目标、构建评测集、设计指标、分析 bad case、搜索候选 prompt， 再用回归测试和 hold-out 测试决定是否上线。

Question

原始问题：Prompt Engineering 能不能变成科学实验？

原始讨论的起点是一个很自然的类比：模型训练可以定义 loss，用反向传播和梯度下降更新参数； 但自然语言 prompt 是离散文本，修改 prompt 后模型输出会怎么变并不确定。那么，能不能把 prompt 和 output 都 embedding 成连续向量，计算 loss，再找到让 loss 下降的 prompt 修改方向？

核心修正 Prompt Engineering 可以科学化、工程化，甚至部分自动优化化；但不能简单靠 prompt embedding 与 output embedding 的距离来解决。

更准确的表述是：Prompt Engineering 是在一个离散、非凸、部分黑盒、目标函数不完美的空间里做行为优化。 它没有天然可微的端到端 loss，所以必须人为定义任务、数据集、指标、对照组、回归测试、bad case 分类和版本管理。

Brief Correction

只保留一个必要纠正：Embedding 不是主指标

Prompt 和 output 的 embedding 距离不是 Prompt Engineering 的核心目标。Prompt 是指令和上下文， output 是任务结果，它们不需要语义接近。真正要评估的是 output 是否符合目标行为、人工标注或 rubric。

对 BetterMe 来说，主指标应该是 decision correctness、false allow、false block、ASK_MORE recall、 schema validity 和 reason quality。Embedding similarity 最多辅助评价解释文本，不能替代产品行为指标。

Concepts

三类 Prompt：Text、Program、Parameter

01

Prompt as Text

最朴素的自然语言指令，例如“请判断用户访问娱乐网站的理由是否合理”。优点是可读、可审查； 问题是规则太抽象时，模型不知道什么叫合理理由、什么叫 weak reason、ASK_MORE 和 DELAY 的边界在哪里。

02

Prompt as Program

Prompt 不再只是一段话，而是 AI 决策程序：system role、输入字段、decision policy、rubric、 output schema、few-shot examples、validator、fallback、retry 和 eval set 都是可优化对象。

03

Prompt as Parameter

Soft prompt / prefix tuning 把 prompt 变成连续向量。它可以通过梯度下降学习，但不可读， 更接近轻量模型适配，而不是产品经理日常写自然语言 prompt。

Spectrum

从手工 Prompt 到模型训练：完整谱系

原始对话中最重要的知识框架，是把 Prompt Engineering 放在一条连续谱上。越往上， 越适合 AI PM 直接操作；越往下，越接近 ML 工程和模型训练。 

手工 Prompt
   ↓
Evaluation-driven Prompt Engineering
   ↓
Automatic Hard Prompt Optimization
   ↓
Textual Gradient / LLM as Optimizer
   ↓
Soft Prompt / Prefix Tuning
   ↓
Fine-tuning / RLHF / DPO
层级 核心动作 AI PM 应该做到什么
1. 手工 Prompt 人工补规则、补例子、补输出格式、补 fallback。 必须会，但不能停在这里。
2. Eval-driven PE 用 eval set、metric、bad case regression 驱动 prompt / schema / rubric 修改。 AI PM 的基本功，至少要能完整做出来。
3. Automatic Hard Prompt Optimization 让 LLM 生成多个自然语言 prompt 候选，在 eval set 上打分和选择。 进阶能力，适合有评测体系后自动化搜索。
4. Textual Gradient 让 LLM 诊断失败原因，生成自然语言批评，再转成 prompt 修改方向。 进阶能力，适合从 bad case 中提炼修改方向。
5. Soft Prompt / Prefix Tuning 训练连续 prompt 或 prefix 向量。 通常知道边界即可，交给 ML 工程。
6. Fine-tuning / RLHF / DPO 用监督数据或偏好数据训练模型参数。 通常不由 AI PM 独立完成，但要知道何时升级。

BetterMe Case

BetterMe：Prompt as Program 的具体形态

BetterMe 的 AI Checkpoint 不是普通聊天机器人，而是一个行为干预决策器。用户访问 YouTube、Reddit、Instagram、X 等 blocked domain 时，它要基于用户理由、当前任务、 历史访问模式和 strictness 策略，稳定输出 ALLOW、DELAY、ASK_MORE 或 BLOCK。 

System Role:
  你是 BetterMe 的 AI Checkpoint 决策器。

Input:
  - blocked_domain
  - user_reason
  - current_task
  - strictness_level
  - recent_blocked_attempts
  - time_of_day
  - previous_decisions

Decision Policy:
  1. 判断理由强度：strong / medium / weak / insufficient
  2. 判断访问意图：work / learning / break / entertainment / avoidance
  3. 根据 strictness_level 调整阈值
  4. 根据历史行为判断是否存在重复逃避
  5. 输出结构化决策

Output Schema:
  decision: ALLOW | DELAY | ASK_MORE | BLOCK
  reason_strength: strong | medium | weak | insufficient
  risk_level: low | medium | high
  message_to_user: string
  follow_up_question?: string

Fallback:
  信息不足不要猜，优先 ASK_MORE。
可优化对象 BetterMe 例子
指令 不要被“就看一下”“马上回来”等模糊理由轻易说服。
决策 schema 加入 reason_strength、risk_level、cooldown 或 follow_up_question。
Rubric 定义 strong / medium / weak / insufficient 理由边界。
Few-shot examples 给模型看典型 ALLOW、ASK_MORE、DELAY、BLOCK case。
Context 加入最近 30 分钟 blocked attempts 和 previous decisions。
Validator / fallback 检查 JSON 合法性；输出不确定或信息不足时优先 ASK_MORE。
Eval set 每次改 prompt / schema / rubric 后跑全部 regression 和 hold-out。

Datasets

三个数据集：Design、Regression、Hold-out

Prompt Engineering 也需要类似训练、验证、测试的分层。只要你看过某个 case，并根据它修改了 prompt， 这个 case 就不再是纯测试集，而是 optimization set。为了避免 prompt overfitting，需要明确拆分数据集。

Design Evaluation Set

产品经理基于产品策略预设的核心场景，用来保证主路径成立。 例如明确工作理由、模糊理由、娱乐逃避、信息不足、strictness 差异、正当休息、高风险边界。

Regression Evaluation Set

真实线上或 PM review 中标注出来的 bad case，转成 eval case。每次 prompt 改动都必须重跑， 目的是防止旧问题复发。

Hold-out Test Set

日常调 prompt 时不要看具体失败详情，只在阶段性验证时使用。它用于检查泛化能力， 防止 prompt 被调成只会通过眼前这些 case。 

Design Eval Set:      60 条，覆盖产品正向设想的主路径
Regression Eval Set:  持续增长，由 bad case 转化而来，初始 20 条
Hold-out Test Set:    30 条，不参与日常 prompt 修改

每次改 prompt:
  先跑 Design + Regression
  通过后再跑 Hold-out
  Hold-out 明显下降，不上线

每条 eval case 不应只包含输入，还要包含 expected_decision、allowed_decisions、 forbidden_decisions、severity、rationale 和 tags。这样产品判断才能变成可计算和可复核的标准。

Metrics

Metric：把产品判断翻译成可打分标准

Metric 不是“感觉更好”，而是明确回答：什么输出是正确的？什么输出是 fatal error？ 哪些输出可以接受但不完美？理由质量、语气、格式、稳定性和成本怎么判断？

指标 含义 BetterMe 例子
Decision Accuracy 决策是否符合 expected 或 allowed decisions。 应该 ASK_MORE，模型是否真的 ASK_MORE。
False Allow Rate 不该放行却放行，通常是严重错误。 用户明显逃避任务，strictness high，模型仍 ALLOW。
False Block Rate 该放行却拦截。 用户有明确工作理由，模型 BLOCK。
ASK_MORE Recall 信息不足时是否会追问。 用户只说“找资料”，模型是否先追问用途。
Schema Validity 结构化输出是否合法、可解析、符合前端约束。 JSON 是否包含 decision、reason_strength、message 等必要字段。
Reason Quality 解释是否命中关键原因。 是否提到 strictness、历史模式、理由强度，而不是泛泛说“注意专注”。
Safety / Boundary 是否越界、羞辱用户或给出不当心理建议。 用户压力很大时不能羞辱或做心理诊断。
Consistency 同样输入多次运行是否稳定。 同一 case 连跑 3 次，decision 不应大幅摇摆。
Latency / Cost prompt 变长是否导致成本和延迟不可接受。 新增 examples 后效果变好，但 token 成本是否超过收益。 
单 case 评分例子:
  60 分: decision 是否正确
  15 分: reason_strength 判断是否正确
  10 分: schema 是否合法
  10 分: 解释是否符合产品策略
   5 分: 语气是否合适

Fatal errors:
  - 严重 false allow
  - 输出 schema 非法
  - 高风险场景给出不当建议

Search

Automatic Hard Prompt Optimization：更像搜索，而不是梯度下降

Automatic Hard Prompt Optimization 仍然输出自然语言 prompt。它通常不是数学梯度搜索， 而是“生成候选 prompt → 跑 eval → 打分 → 选择高分 → 继续变异或改写”的搜索过程。 

当前 prompt + 产品目标 + eval 结果 + 失败摘要
        ↓
LLM 生成多个候选 prompt
        ↓
每个候选在同一套 eval set 上跑分
        ↓
选择 trade-off 最好的版本
        ↓
继续变异 / 合并 / 压缩 / 加例子
        ↓
Regression + Hold-out 后决定是否上线

给 LLM 的改写方向必须具体。不能只说“让这个 prompt 更好”，而应该把失败类型和产品约束一起给它。

变异方向 具体动作
降低 false allow 加入 weak reason examples，明确 high strictness + repeated attempts 禁止直接 ALLOW。
提升 ASK_MORE recall 把信息不足、理由过短、目标不明确的 case 优先改为 ASK_MORE。
降低 false block 补充真实工作理由和学习理由的正例。
改善解释质量 要求解释必须引用理由强度、strictness 或历史行为中的关键因素。
压缩 prompt 删除冗余规则，保留 high-impact examples，降低 token 成本。

相关方法可以这样理解：APE 让 LLM 自动生成候选 instruction；OPRO 把历史候选和分数放进上下文， 让 LLM 继续生成更高分的新方案；PromptBreeder 和 EvoPrompt 用更接近进化算法的变异、选择和交叉搜索 prompt； RLPrompt 则用强化学习生成离散 prompt，但结果不一定人类可读。

Diagnosis

Textual Gradient：更像诊断，而不是搜索本身

Textual Gradient 和 Automatic Hard Prompt Optimization 的区别，可以用一句话记住： 前者偏诊断，后者偏搜索。

Automatic Hard Prompt Optimization

生成很多候选版本，跑分，选高分。它回答的是“哪个候选更好”。

Textual Gradient

分析失败原因，生成自然语言批评，再根据批评修改 prompt。它回答的是“为什么失败，应该朝哪里改”。

失败 case:
  Domain: youtube.com
  Reason: “我就看一个视频”
  Strictness: high
  History: 最近 30 分钟 5 次访问
  Model: ALLOW
  Expected: DELAY 或 BLOCK

Textual gradient:
  当前 prompt 没有明确说明 repeated attempts 会提高风险等级。
  它也没有定义 weak reason，例如“就看一下”“马上回来”。
  因此模型把用户承诺当成可信理由，导致过度放行。

修改方向:
  1. 在 reason_strength rubric 中加入 weak reason 示例。
  2. 在 strictness = high 规则中加入 repeated attempts 条件。
  3. 明确 weak reason + repeated attempts 时禁止直接 ALLOW。

ProTeGi / APO 的思想就是用自然语言“梯度”批评当前 prompt，再按这个方向编辑 prompt； TextGrad 则把这种思想扩展成更通用的框架，让 LLM 产生文本反馈并“反传”到 prompt、代码、回答或系统组件。

PEFT

PEFT：当 Prompt as Parameter 进入轻量训练

PEFT 是 Parameter-Efficient Fine-tuning，核心目标是在不全量更新大模型所有参数的情况下，让模型适配特定任务或风格。 在这条谱系里，soft prompt / prefix tuning 属于 PEFT 的 prompt-based 方法，但 PEFT 不只这一类。

Prompt-based 方法

学习 soft prompt、prefix 或 p-tuning 向量。模型主体冻结，只训练少量“虚拟 token”或 prefix 参数。 优点是参数少，缺点是不可读，且需要可训练模型或训练接口。

Adapter 方法

在 Transformer 层中插入小型 adapter 模块，只训练这些新增模块。优点是任务隔离和可插拔； 缺点是会改变模型结构或推理路径。

Weight Delta 方法

不直接训练完整权重，而是训练权重增量或低秩更新，例如 LoRA。部署时可以把 delta 与基础模型组合， 在较低成本下学习任务特定行为。

Full Fine-tuning 对比

Full fine-tuning 更新全部模型参数，表达能力最强，但训练成本、存储成本、过拟合风险和模型治理成本都更高。 PEFT 用更少参数换取更低成本和更好的多任务管理。 

Hard Prompt:
  人类可读，但不可微，主要靠 eval + search + diagnosis。

Soft Prompt / Prefix:
  不可读，但可微，可以用反向传播学习连续向量。

Adapters / LoRA:
  不改或少改基础模型，用少量可训练参数适配任务。

Full Fine-tuning:
  更新全部参数，成本最高，也最接近真正模型训练。

对 AI PM 来说，关键不是亲自训练 PEFT，而是知道边界：当 hard prompt 已经很长、eval 仍不稳定、 有大量高质量标注数据、并且需要长期稳定的产品行为时，才值得把问题升级给 ML 工程。

Alignment

Fine-tuning / RLHF / DPO：什么时候超出 Prompt Engineering

Fine-tuning、RLHF 和 DPO 已经进入模型训练或对齐，不再是普通 prompt editing。 它们适合决策风格长期稳定、有大量高质量标注或偏好数据、prompt 已经过长或 few-shot 仍无法覆盖复杂行为的阶段。

Fine-tuning

用监督数据让模型直接学习任务输出。适合目标稳定、数据充足、希望减少长 prompt 的场景。

RLHF

收集人类偏好，训练 reward model，再用强化学习让模型更偏向人类喜欢的回答。

DPO

同样利用偏好数据，但把偏好优化转成更简单的训练目标，减少传统 RLHF 的复杂流程。

BetterMe 类比

同一个 checkpoint case 下，人工标注 B 输出比 A 输出更符合专注策略，大量偏好对可用于 DPO / RLHF。

对 AI PM 最关键的是前四层：会写 AI decision policy，会把 bad case 转成 eval case，会定义 metric， 会用 eval 结果驱动 prompt / schema / workflow 迭代。第 3 层和第 4 层可以逐步自动化； 第 5 层和第 6 层通常不是 AI PM 独立执行，而是判断何时升级到 ML 工程。

Paper Map

论文速查表：知道它们在谱系里的位置

方法 核心思想 在 BetterMe 里的类比
AutoPrompt 用梯度引导搜索 prompt token，偏 white-box。 说明 prompt 可以被算法搜索，但不太适合直接做可维护产品 prompt。
APE 让 LLM 自动生成候选 instruction，再用任务分数选择。 生成 20 个 AI Checkpoint prompt，在 eval set 上选最好。
OPRO 把历史候选和分数放进上下文，让 LLM 继续提出更高分方案。 把 v1/v2/v3 分数喂给 LLM，让它生成 v4/v5。
ProTeGi / APO / TextGrad 用自然语言批评当前 prompt，再把批评转成修改方向。 evaluator 总结“没有定义 weak reason”，optimizer 据此改 rubric。
DSPy 把 LM pipeline 写成可优化程序，用 metric 优化 prompts、examples 或 pipeline。 把 BetterMe checkpoint 写成模块，而不是维护一大段不可测试 prompt。
Prefix / Prompt Tuning 冻结模型，学习连续 prefix 或 soft prompt。 有大量标注数据和可训练模型后，学习 BetterMe 专用决策风格。
LoRA / Adapters 只训练少量新增参数或低秩权重增量。 比 full fine-tuning 更低成本地适配模型行为。
RLHF / DPO 用人类偏好数据对齐模型输出。 PM 对两个 checkpoint 输出做偏好标注，训练模型更符合策略。
