Prompt Engineering 科学化探索

Prompt Engineering 不应该被理解成“改一句话”。从 AI PM 视角，它更像一套 AI 行为优化系统：定义行为目标、构建评测集、设定 metric、分析 bad case、管理版本， 再决定是否引入自动优化或训练。

Question

问题不是“Prompt 是否玄学”，而是你有没有把它工程化

原始讨论从一个直觉开始：训练模型时可以定义 loss，通过反向传播找到参数更新方向； 但修改自然语言 prompt 时，模型输出变化不确定，似乎无法知道该改哪个字、朝哪个方向改。

更严格的回答是：手工改 prompt 往往只是经验实验；但只要定义任务、样本、指标、 对照组、回归测试、错误分类和版本管理，它就可以成为工程化实验。再进一步，如果有假设、 控制变量和统计比较，它也可以接近科学实验。

核心结论 Prompt Engineering 可以被科学化，但不能靠 prompt / output embedding 距离直接解决。

Concepts

三类 Prompt：Text、Program、Parameter

01

Prompt as Text

一段自然语言指令，例如“请判断用户访问娱乐网站的理由是否合理”。它容易开始， 但也最容易变成凭感觉调文案。

02

Prompt as Program

把 prompt 当成 AI 决策流程来写，包含输入字段、决策策略、rubric、few-shot、 输出 schema、fallback 和评测约束。

03

Prompt as Parameter

连续 prompt 或 soft prompt，不再是人类可读文本，而是通过训练得到的一组向量。 这更接近 ML 工程，不是多数 AI PM 的起点。

Method

把 Prompt Engineering 科学化的正确路径

1

定义产品行为

先说清楚模型在业务里应该做什么，而不是先问 prompt 写得是否优雅。

2

构建 Eval Set

把典型正例、边界 case、真实 bad case 和隐藏 holdout 分开管理。

3

定义 Metric

把“好不好”拆成 decision correctness、schema validity、reason quality、tone、latency 和 cost。

4

做版本化实验

每次改 prompt、schema、rubric 或 examples，都跑回归并记录版本差异。

5

用 Bad Case 驱动改进

不是只收集失败样本，而是标注错误类型、严重程度、原因和可接受替代输出。

BetterMe Case

以 BetterMe AI Checkpoint 为例

BetterMe 的 AI Checkpoint 不是普通聊天机器人。它像一个行为干预决策器： 当用户访问 YouTube、Reddit、Instagram、X 等 blocked domain 时，需要根据用户理由、 当前任务、历史访问模式和 strictness 策略输出 ALLOW、DELAY、ASK_MORE 或 BLOCK。

Prompt as Program 应该定义什么

Input

blocked domain、user reason、current task、strictness、recent attempts、previous decisions。

Decision Policy

判断理由强度、访问意图、重复逃避风险，并按 strictness 调整阈值。

Output Schema

结构化输出 decision、reason_strength、risk_level、message、cooldown 或 follow-up question。

Fallback

信息不足优先 ASK_MORE；输出格式非法时重试或走保守 fallback。

Metric 怎么判断 为什么重要
Decision correctness 是否输出期望决策或可接受决策。 直接决定产品干预是否正确。
False allow 高风险或逃避场景被放行。 这是专注类产品最严重的失败之一。
False block 真实工作或学习理由被误杀。 会破坏信任，用户会绕过产品。
ASK_MORE recall 信息不足时是否追问，而不是猜测。 能减少草率的 ALLOW 或 BLOCK。
Schema validity JSON 是否稳定符合前端和存储约束。 AI 产品需要可执行输出，不只是自然语言解释。

Optimization

Embedding loss、Textual Gradient 和 Soft Prompt 的边界

为什么不能只算 embedding 距离

Output embedding similarity 不等于任务正确。两个回答语义接近，但一个可能放行， 一个可能延迟；对 BetterMe 来说，这就是完全不同的产品行为。

Textual Gradient 更适合 hard prompt

它不是数学梯度，而是让 LLM 根据失败样本生成自然语言批评，再把批评转成 prompt、 rubric 或 examples 的修改方向。

Soft Prompt 更接近训练

Prefix tuning 和 prompt tuning 会学习连续向量，适合有可训练模型、大量标注数据、 ML 工程资源，并愿意牺牲可读性的阶段。

Fine-tuning 不是第一步

当 prompt、schema、eval 和错误归因都无法解决稳定失败模式，且有足够数据时， 再考虑 fine-tuning、RLHF 或 DPO。

Interview

AI PM 面试里可以这样讲

不要说“我会把 prompt 写得更好”。更强的表达是：我会先定义模型在产品场景中的目标行为， 再用 eval set 和 metric 判断每次改动是否真的改善了行为。

以 BetterMe 为例，我优化的是 AI Checkpoint 的决策质量，而不是一句提示词。 我会定义 decision policy 和 strictness rubric，把 bad case 转成 regression case， 每次修改 prompt、schema 或 examples 后观察 false allow、false block、ASK_MORE recall、 schema validity 和 reason quality。只有在有稳定评测体系后，我才会引入自动 prompt 优化。
